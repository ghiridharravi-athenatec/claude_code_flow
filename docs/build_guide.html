LAB: Medical Record Validator (CDI Scorer)

Disclaimer

This document reconstructs the actual Define → Build → Validate workflow used to build the CDI Scorer in a real Claude Code session — the real SCOPE.md/SPEC.md/CLAUDE.md content, the real code, and real captured terminal output are quoted throughout, not illustrative placeholders. Every rubric dimension's keyword/regex indicators were authored by Claude Code as a deterministic matching layer — there is no LLM call at scoring time and no clinical judgment; this is a demonstration app and must not be used for real clinical or billing decisions.

Objective

Provide a reproducible record of how an AI-assisted clinical-documentation review application was actually built with Claude Code: upload a medical record (PDF / TXT / DOCX), extract its text, score it against the fixed 10-dimension, weighted, narrative med_record_rubrics.json rubric using purely deterministic keyword/regex matching (no LLM judgment), and return a structured score / decision-band / gaps report through a Flask backend and a React front end.

Prerequisites

  • Python 3.11+ (this build session ran on Python 3.14.7) and Node 20+ (this session used Node 24.19.0)
  • No OCR, no Tesseract, no Poppler — SCOPE.md explicitly excludes OCR/scanned PDFs (text-layer PDFs only)
  • No ANTHROPIC_API_KEY needed at runtime — scoring is 100% deterministic keyword/regex matching, not Claude-judged
  • On Windows: python-magic needs a native libmagic — requirements.txt resolves this with a platform marker (python-magic-bin on win32)

STEP 2 · Write the System Specification LLM

What actually happened: SPEC.md (320 lines) was already the binding contract for this session — architecture, extraction pipeline, PHI rules, the matching algorithm, the response JSON schema, and the full API contract. Real scoring rule, quoted directly:

SPEC.md §2.1 / §2.3 (real file, excerpt)
formula: points = (score / 5) * weight   # per dimension
total:   sum of all ten dimensions, 0–100

decision_bands:
  88–100  DOCUMENTATION ACCEPTED
  74–87   ACCEPTED WITH QUERY
  58–73   RETURN FOR CLARIFICATION
   0–57   DEFICIENT

hard_rules:
  HR-1  R1 (Authentication) == 1  ->  DEFICIENT            # overrides weighted band entirely
  HR-2  R5 (Diagnostic Specificity) == 1  ->  RETURN FOR CLARIFICATION
Why the hard-rule override exists: a documentation-integrity rubric can't let a high weighted average paper over an unauthenticated record (R1) or a diagnosis the narrative can't support (R5) — the spec makes those two dimensions capable of overriding the weighted-band lookup entirely, and my scorer.py implements exactly that precedence (see Unit 7).

## The rubric file is READ-ONLY to generated code
- Never write code that modifies, regenerates, or "fixes" this file.
- Load it exactly once, at app startup, in rubric_loader.py.

## PHI handling — hard constraints, not suggestions
1. Never write extracted record text to disk or any persistent store.
2. Never log raw extracted text — pass through phi/redact.py first,
   including exception tracebacks.
4. The ONLY place raw text may flow: (a) the rubric matcher, and
   (b) matched_snippet fields in the JSON response.

## Golden regression suite — must always pass
- Never edit an existing golden fixture to make a failing test pass.
Standing rule that made every later slice trustworthy: "If a task seems to require changing this file's structure ... stop and ask rather than editing it" — this is CLAUDE.md's version of the reference guide's "self-check before done" rule: a hard boundary Claude Code was not permitted to cross silently.

UNIT 6 — DETAILED STEPS (REAL ARTIFACTS)
STEP 4 · Claude Code Builds It Claude Code

What actually happened: this is where this Claude Code session's real work is — not a scripted SDK loop, an ordinary interactive session using Write/Edit/Bash tools directly, slice by slice, matching the phase breakdown the reference guide uses for its own SDK runs:

  1. Backend scaffold — config.py, extraction/errors.py, detect.py, per-type extractors (pdf_extractor.py, docx_extractor.py, txt_extractor.py).
  2. PHI module — phi/presidio_config.py (custom AADHAAR/PAN regex recognizers + Presidio defaults), phi/redact.py (the single redaction helper).
  3. Schemas — schemas/validation_result.py, dataclasses mirroring SPEC.md §3 field-for-field.
  4. Validation engine — rubric_loader.py (load-once), dimension_indicators.py (hand-authored keyword/regex indicator sets, 10 dimensions × 5 levels, derived from the rubric's own prose), matcher.py (top-down level assignment), scorer.py (weighted aggregation + hard rules).
  5. API wiring — routes/health.py, routes/rubrics.py, routes/validate.py, app.py (application factory, blueprint registration, CORS).
  6. Tests — test_extraction.py, test_matcher.py, test_golden.py + two golden fixtures, test_api.py.
  7. Frontend — App.jsx, api/client.js, all five components, styles.
One real "loop needed" moment inside this step: requirements.txt initially pinned spacy==3.7.5 — that pin has no prebuilt wheel for this machine's Python 3.14, so a clean install failed compiling blis/thinc from source. Relaxed the pin to spacy>=3.7.5; a fresh venv then installed clean and all 24 tests passed. This is the same category of "self-check catches an environment gap" moment the reference guide's judged-scorer failure illustrates (Unit 6, Step 6/8) — except this one was diagnosed and fixed within Step 4, not carried forward as an accepted gap.

Every response field is a dataclass, not a bare dict crossing a function boundary. Real excerpt from backend/schemas/validation_result.py:

@dataclass
class DimensionResult:
    rubric_id: str
    name: str
    weight: int
    score: DimensionScore          # int 1-5, or literal "N/E"
    points_earned: float
    matched_level_text: str
    matched_snippet: str | None
    hard_rule_triggered: str | None

API contract (base path /api/v1, no auth, no persistence — matching SPEC.md §4 exactly):

Method & pathPurposeSuccess
POST /validateupload + extract + score, synchronous200, schema in SPEC.md §3
GET /rubricsmetadata for the single active rubric200
GET /healthliveness200 {"status":"ok"}
Coding conventions actually enforced: type hints on every signature; specific exception classes (ExtractionError subtypes), never bare except:; PHI redaction isolated to phi/redact.py, imported everywhere else rather than reimplemented; rubric content always read from med_record_rubrics.json, loaded exactly once at startup, never re-read per request, never written to.
